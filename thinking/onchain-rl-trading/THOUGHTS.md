### 助手提出的问题结构（待用户校正）

用户的一句话请求实际上捆绑了三个可分离的决策，把它们拆开是本次探究的第一个动作：

1. **交易问题本身**：盈利来源（edge）的假设是什么？在链上，可信的 edge 类型至少包括：跨场所/跨池价差、清算与套利、做市价差、资金费率、以及方向性预测。不同 edge 的可验证性和竞争强度差别巨大。
2. **RL 作为方法的定位**：RL 是解决"该不该买、买多少"（端到端策略）还是"已决定要交易，如何最优地执行/管理仓位"（子问题优化）。
3. **链上执行的工程约束**：区块时间、gas 成本、MEV / 三明治攻击、滑点与价格冲击、RPC 延迟、私钥与合约安全。这些不是实现细节，而是会反过来否决某些策略类别的硬约束。

### 助手的初步判断（**假设，非结论**，需在 Research 阶段验证）

- **H1 — RL 在此的成败主要取决于环境保真度，而非算法选择。** 链上交易的仿真难点不在价格序列回放，而在执行侧的反身性：自己的订单会改变 AMM 池价格、可能被抢跑或夹击、可能因拥堵而交易失败。若训练环境不复现这些，RL 会系统性地学到在实盘不成立的策略，且偏差方向是**高估收益**。
- **H2 — 金融序列的低信噪比与非平稳性，使 RL 的样本效率问题在此格外致命。** 这是文献中 RL 交易结果大量无法复现的常见原因（前视偏差、过拟合、未计成本）。此判断需以具体文献核实，当前仅为待验证假设。
- **H3 — 更可能成立的切入点是"有即时反馈、状态可观测、可反事实仿真"的子问题**：执行拆单、仓位与杠杆管理、做市报价、gas/滑点参数自适应——而非端到端 alpha 生成。若 H3 成立，则用户"以 RL 为主"的诉求需要重新定义"主"的所指。
- **H4（候选 Alpha，助手提出）— "链上"这一约束同时提供了一个传统市场不具备的独特优势：状态可完整重放。** EVM 链可以 fork 到任意历史区块、在真实合约状态上重放自己的交易（Foundry/Anvil fork 模式），从而获得**远高于传统回测**的执行保真度——包括真实滑点、真实 gas、真实失败。如果 H1 成立（保真度是瓶颈），而链上恰好能提供高保真环境，那么本项目真正的差异化可能不在 RL 算法，而在"用链上可验证重放构建高保真 RL 训练环境"这一基础设施。此判断的外部独创性（是否已有成熟实践）尚未核查。

## 已核验证据

### E1 — HRT 一手来源（**助手直接核验**）

- **来源**：Hudson River Trading 官方技术博客，"Applying Artificial Intelligence to Trading"，2021-09-15，https://www.hudsonrivertrading.com/hrtbeat/ai-trading/
- **核验方式**：助手于 2026-09-07 用 exa 抓取全文并逐句阅读，非转述。
- **HRT 列出的、AlphaGo 范式无法迁移到交易的四条结构性障碍**（原文要点）：
  1. **非零和**：市场对参与者效用而言非零和。"**we cannot use HRT's AI as a proxy for the other 'players', which is a key component of how AlphaGo works. Instead, we would need to model a wide variety of different types of 'players'**"
  2. **规则不完全已知**：不知道发出订单后确切会发生什么；若他人同时下单，结果是随机的。
  3. **状态非完全可观测**：历史对预测至关重要，且每一瞬间都含隐藏信息（他人身份与仓位、隐藏订单类型）。
  4. **数据非无限**："**in trading we have only one reality, and acquire new data in real time – i.e., very slowly.** We can attempt to produce data by simulating many different AIs against each other, but **it is a poor proxy for the rich complexities and interactions of the real world**"
- **HRT 的应对：三层分解**（原文）：
  - **预测层**："it just needs to solve this '**supervised**' learning problem"；"Many of our researchers spend most of their time on this subproblem."
  - **优化层**："**Financial mathematics has many solutions to this problem already, so we don't have to take an AI perspective here at all necessarily**"
  - **执行层**："Trading off all these concerns is a complex problem, but simpler than taking them all together, and **one we can try to train an AI to do**. Still, **this problem is in many ways the hardest** as it hits the issues we described above – **our actions can have immediate consequences that are hard to reason about, unlike in a game**."
- **对本探究的效力**：
  - **强力支持 H2**（样本效率/唯一现实）与 **H3**（分解到子问题）。障碍 4 是 H2 的一手权威表述。
  - **强力支持 H1** 的机制：障碍 1、2 正是"执行反身性"。
  - **但同时收窄 H4**（见下）。
  - **适用性限制**：HRT 讨论的是传统交易所市场（2021 年），非链上。其"仿真是拙劣代理"的论断建立在"传统市场状态不可重放"这一前提上；该前提在链上不成立，故不能直接照搬结论，但其**分类框架**可迁移。

### E4 — 执行吞吐（**助手直接核验，这是原先缺失的决定性数据**）

| 测量 | 数值 | 来源（助手直接读取，2026-09-07） |
| --- | --- | --- |
| revm 单线程模拟一次 **Uniswap swap**，状态全在内存 | **175,011 ns/iter ≈ 175 µs → ~5,700 次/秒** | `cassc/rust-evm-bench`，https://github.com/cassc/rust-evm-bench |
| revm 单线程 ERC20 transfer，同上 | 8,010 ns/iter ≈ **~125,000 次/秒** | 同上 |
| revm 顺序执行主网真实区块 | **1,212–1,258 MGas/s** | "Achieving 10GigaGas/s EVM Execution with BAL"，https://hackmd.io/7_3yUSGnRzGPTUtvj78W1A |
| revm 16 线程并行，主网真实区块 | **5,084 MGas/s** | 同上 |
| REVM + FAFO 调度器，96 核 | 1.12M native / **566k ERC20 转账每秒** | arXiv:2507.10757，https://arxiv.org/html/2507.10757 |

- **交叉验证**：Uniswap V3 swap 约 120–180k gas；按 1,212 MGas/s 顺序吞吐反推 ≈ **8,000 swap/s 单线程**，与直接测得的 5,700/s **同一数量级**。两个独立来源相互印证。
- **推论 C1（决定性）**：**EVM 执行不是 RL 训练的瓶颈。** 10^6 步 ≈ 单核 3 分钟；10^7 步 ≈ 单核 29 分钟，多核可再降一个数量级。**原先担心"fork 仿真太慢因而 H4' 不可施工"的顾虑，被证据推翻。**
- **推论 C2（新的真瓶颈）**：瓶颈在**历史状态获取**（archive node RPC / trace_callMany），而非 EVM 计算。hindsight 自己的成本警告与 175 µs 基准的前提（"all states kept in memory"）共同指向这一点。
- **推论 C3（架构含义）**：既然 EVM 便宜、状态贵，正确的架构是**按历史区块预热一次 ForkDB（state diff 缓存），然后在这个内存快照上跑成千上万个 RL step**，把昂贵的 archive 访问摊薄到大量采样上。这把"每步一次 RPC"（ScalingEthereum 的做法）变成"每个 episode 一次状态加载"。

## H4 的实质性收窄（基于 E1）

**原 H4**：链上状态可完整重放 → 可构建远高于传统回测保真度的 RL 环境。

**修正后 H4'**：链上重放提供的是**我方动作机械后果的保真**（真实滑点、真实 gas、真实 revert、真实池状态），**不提供对手反应的保真**。HRT 障碍 1、2 在链上**依然成立**：
- 重放历史区块时，其他参与者的行为是**已录制的**，不会对我方的介入作出反应；
- 我方交易一旦被打包，后续区块状态即与历史分叉（**反事实分叉问题**）；
- mempool 竞争、抢跑、区块构建者排序权无法由重放复现。

**结论**：H4' 把链上的优势精确限定为"**高保真的单边执行仿真**"。这仍是传统市场不具备的能力，且恰好覆盖 HRT 所说"最难、且我们会尝试训练 AI"的**执行层**。但它**不能**支撑端到端 alpha 的可信训练，因为那需要对手反应保真。

**这一收窄若成立，则本项目的可辩护定位是**：用链上可重放性构建高保真**执行/仓位**环境，把 RL 用在 HRT 认定"最难但可训练"的那一层——而非端到端策略。此定位待 B1/B2 证据进一步支持或推翻。

## 备选、Alpha 与异议

- 助手对用户前提的最主要异议：**"以 RL 为主"是先固定了手段再定义问题**。若 edge 假设与执行约束尚未确定，RL 的选择就无法被评估其是否恰当。此异议按 Frame 阶段规则在建立于该前提之上的工作开始前提出，供用户判断是否调整框架。
- 用户可以在听取该异议后仍坚持"RL 为主"（例如目的本身就是研究 RL 在链上环境的应用，而非最大化收益）。若如此，探究的目标函数将从"做出可盈利系统"改为"做出方法上可信的 RL 链上交易研究"，二者的"足够好"标准完全不同。这一点需要用户明确。

## 候选定位 A2（助手提出，替代第一轮的定位）

> **Edge 不在预测价格，在于「知道谁将被迫成交、何时、多大量」，然后作为流动性提供方系统性地站在被迫方对面。**

- **⚠️ 助手对自己这个定位的最强反对**：**清算图是公开信息，人人可算。** 公开信息能否承载 edge，取决于 (a) 实时大规模计算它是否构成工程壁垒（跨保证金 + funding 累积下精确算全网清算价，确实不平凡）、(b) 反应是否需要基础设施与资本、(c) 多少参与者实际在用。**(c) 不能假设为"很少"。** 因此诚实的表述是：**清算图是必要的状态变量，不是充分的 edge**；edge（若有）来自在其上的策略，而这正是 model-based 规划可能优于手写规则之处。此反对尚未被证据解决。
