# 第一部分 · 项目定义

## 1.1 一句话

**把交易场所的机制写成可执行的会计核心，用链上真值每天自动校验它；在这个被校验过的机械动力学上做规划与执行；用 agent 承担读文档、提假设、诊断漂移这类语义工作，但所有产出都必须落到机器可判定的验收上。**

## 1.2 系统要回答的三个问题

| 阶段 | 问题 | 由谁回答 |
|---|---|---|
| **发现** | 这个场所的机制里，哪里有可利用的结构？ | 接缝扫描（对 spec 的静态查询）+ agent 提议 |
| **建模／仿真** | 这个结构是真的，还是在给某个成本定价？ | 零假设证伪 + 八关 gauntlet |
| **执行** | 在真实约束下能不能稳定拿到它？ | T1→T2→T3→小额真钱的保真度阶梯 |

## 1.3 边界

**做**：Hyperliquid（主 perp dex + HIP-3 tradeXYZ）作为第一个场所；机制驱动策略与传统 CTA 两类策略共用同一条流水线；从零到小额真钱的完整通路。

**不做（本期）**：多场所（架构支持，但先只落一个）；EVM AMM 侧（接口预留）；做市以外的高频路径；自建撮合引擎。

**永不做**：让 agent 进入下单决策路径；让 agent 评判策略是否有效；在没有链上真值对账的情况下上真钱。

## 1.4 非目标（明确排除，防止范围蔓延）

- **不造通用 DSL**。spec 用 Rust/Python 直写，等三个场所之后再考虑抽象。
- **不指望 spec 生成仿真器**。spec 只覆盖会计核心，撮合交给 Nautilus + 明确标注的假设。
- **不追求「一套求解器跑所有场所」**。那是架构整洁性，不是研究效率。
- **不做学习型世界模型**（Dreamer/MuZero 类）。

# 第二部分 · 核心抽象

三个抽象贯穿全系统。每个模块的设计都应能追溯到其中之一。

## 2.1 状态分解：p 与 m

```
s = (p, m)

p  外生价格    转移不可知          → 预测器输出【分布】，承认信息天花板
m  机械状态    转移是已发布的公式   → 写死，不学；且【依赖你的动作】
a  动作        受 m 的硬约束        → 保证金、discovery bounds、订单上限
r  奖励        (m, p) 的闭式函数    → 费用/funding/滑点/清算罚金全可算
```

**工程含义**：
- `m` 的转移函数 = **会计核心**（第 4 章）。它是代码，不是模型。
- `p` 的预测 = **price 模块**（第 6 章）。它是可替换的，且**独立记账**。
- 策略在 `m` 上做规划，把 `p` 的分布当作不确定性输入。
- **CTA 是这个框架的特例**：`m` 很薄（只有保证金与 funding 会计），`p` 承担全部。它照样跑同一条流水线，且**可以吃到 m 通道产出的特征**——这是 CEX 上的 CTA 拿不到的输入。

## 2.2 三方对账

```
会计核心 spec  ←→  Nautilus 账户状态  ←→  链上真值
```

**任意两方不一致 = 信号，且三种故障可被区分**：

| 不一致的两方 | 诊断 |
|---|---|
| spec ≠ 链上 | spec 错，或场所改了参数 → 触发漂移分诊 |
| Nautilus ≠ 链上 | 适配器或撮合建模不符 → 修适配器 |
| spec ≠ Nautilus，但都 = 链上 | 口径差异（如舍入、时点）→ 对齐口径 |

**这是整个系统唯一的、也是全部的护城河**：手写回测器的错误要亏钱才发现，这套东西 CI 当天就报。

## 2.3 提议与裁决

> **Agent 与人的产出都是「提议」。每条提议落到一个预注册的、机器可判定的验收上。提议者不是裁判。**

这条规则同时管住三件事：agent 幻觉、研究者的 p-hacking、以及外部不可信内容（场所文档、治理论坛）对系统的影响。

**唯一的授权者是验收通过，不是提议者的置信度。**

# 第四部分 · 层 A / B 详设：数据与会计核心

## 4.1 A1 · 行情录制（`svc-recorder`）

**职责**：录制不可追补的行情基座。

| 项 | 规格 |
|---|---|
| 采集 | Hyperliquid WS：`l2Book`（增量 + 5s 全量快照）、`trades`（带 `users[buyer,seller]`）、`activeAssetCtx`、`userEvents` |
| 覆盖 | 主 perp ≥3 标的 + HIP-3 ≥3 标的（含至少一个休市会话品种，如 `xyz:CL` 或 `xyz:SP500`） |
| 存储 | Parquet，按 `venue/market/date/hour` 分区；每个文件带 manifest（采集起止、序列号连续性、缺口标记、采集器版本、schema hash） |
| 完整性 | 序列号连续性检查；缺口显式记录为 `gap` 行而非静默跳过 |
| 交叉校验 | 每小时从录制重建 `impact_bid_px`/`impact_ask_px`，与同时刻 API `impactPxs` 比对，差异入监控 |

**⚠️ 第 0 天启动。** 官方 S3 的 `l2Book` 是按小时目录、约每月上传一次、不保证及时、可能缺失——指望不上。**每晚一天就永久少一天可校验的历史。**

## 4.2 A2 · 全局状态（`svc-state`）

**职责**：维护全网持仓与清算图，而不是公网 API 的抽样。

| 项 | 规格 |
|---|---|
| 节点 | Hyperliquid 非验证节点，16 vCPU / 128GB RAM / 500GB SSD，约 100GB 日志/天 |
| 全量快照 | `periodic_abci_states`（每 10,000 块）→ `translate-abci-state` → 结构化 |
| 全簿 | `compute-l4-snapshots --includeUsers`（含每笔挂单归属） |
| 本地查询 | `--serve-info` 起本地 info server（官方称可缓解限速） |
| 增量 | WS `trades` 的 `users[]` 反推活跃地址；`userEvents.WsLiquidation`、`WsFill.liquidation`（**区分 `market` 与 `backstop`**） |
| 历史回补 | S3 `node_fills_by_block` / `misc_events_by_block`（requester-pays） |

**为什么必须自建**：公网 API 限速 1200 权重/分钟，`clearinghouseState` 权重 2 → 600 账户/分钟；扫完 4.5 万地址需 75 分钟/IP；实测按权益 top 2,498 账户只还原全局 OI 的 34.9%。**公网 API 做不了实时全局状态。**

**产出**：`LiquidationMap`——按 (market, price_bucket) 聚合的强平量分布，附重建时点与覆盖率。

## 4.3 A3 · Nautilus 数据平面接入

**职责**：复用事件溯源与数据目录，不自造。

- 录制数据 → Nautilus `DataCatalog`（Parquet）
- 回放产出的 `OrderBookDeltas` 与原始录制**字节级等价**（有测试）
- 确定性仿真测试：同 seed 两次运行的事件序列哈希一致
- **不 fork Nautilus 引擎**——增量以插件/策略/独立模块形式存在（LGPL 合规）

## 4.4 B1 · 会计核心（`accounting-core`）

**职责**：`m` 的转移函数。300–800 行可执行代码。

### 写进 spec 的（Hyperliquid，字段均已核验）

```
funding:
  F = avg_premium + clamp(0.0001 − premium, −0.0005, +0.0005)
  premium 每 5s 采样、按小时平均、按 1/8h 支付、封顶 4%/h
  impact_price_difference = max(impact_bid − oracle, 0) − max(oracle − impact_ask, 0)
  impact notional = 20,000 USDC (BTC/ETH) / 6,000 USDC (其他)
  ★ 结算用 spot oracle price 换算名义值，不是 mark price
  ★ HIP-3 用【不同的】公式：premium = 0.5*(impact_bid+impact_ask)/oracle − 1（无 clamp）

margin:
  maintenance = 最大杠杆下初始保证金的一半 → 1.25%(40x) ~ 16.7%(3x)
  分档：mm_rate(tier n) = (tier n 初始保证金率)/2
       mm_deduction(n) = mm_deduction(n−1) + notional_lower_bound(n)*(mmr(n)−mmr(n−1))
  cross 的清算价不依赖所设杠杆；isolated 依赖

liquidation:
  liq_price = price − side*margin_available/position_size/(1 − l*side)
  l = 1/MAINTENANCE_LEVERAGE（分档资产取清算价对应档位）
  notional > 100k USDC → 市价单只发 20%；之后 30 秒冷却期内改为整仓
  权益 < (2/3)*mm → backstop 转 HLP，维持保证金不退还

adl:
  rank = (mark_price/entry_price) × (notional_position/account_value)
  按上一个 mark price 与反向持仓的盈利用户成交

constraints:
  max_market_order_ntl = {≥25x: 30e6, 20–25x: 5e6, 10–20x: 2e6, else: 500e3}
  max_limit_order_ntl = 10 × max_market
```

### 不写进 spec 的

撮合逻辑、队列位置、部分成交顺序。**理由：HL 不公开 L3，校验不了的东西不要 spec。** 用「在明确的队列假设下重建的 virtual MBO」，假设写进 manifest 并随每份结果输出。

### ⚠️ 静默错算陷阱

**HIP-3 perps 与普通 perps 用完全不同的 premium 公式。** spec 必须带 market 类型判别（`market_class: perp | hip3`），且对账必须覆盖两类。没有这个判别，整套系统会**静默地**算错，且不报错。

## 4.5 B2 · 三方对账（`conformance`）★关键闸门★

**命令**：`make conformance --months 3`

| 校验项 | 真值来源 | 容差 |
|---|---|---|
| 每小时 funding rate | `metaAndAssetCtxs.funding` | 精确（最小计价单位） |
| 每笔 funding payment | 账户 `cumFunding` 增量 | 最小计价单位 |
| `liquidationPx` | `clearinghouseState.assetPositions[].position.liquidationPx` | ≤1 tick |
| 清算触发区块 | `userEvents.WsLiquidation` / `misc_events` | ≤1 block |
| `markPx` / `premium` / `openInterest` | `metaAndAssetCtxs` | 最小计价单位 |
| 账户权益 | `marginSummary.accountValue` | 最小计价单位 |

**失败即非零退出。接入每日 CI，有告警通道。**

**停止条件（硬）**：**4 周内此 Anchor 不通过 → 整条路线停。** 这已是最简单场所、最小机制子集、最公开规格。

**成功判据不是「spec 写完了」，是某天 CI 红了、而你发现场所悄悄改了 impact notional。**

# 第五部分 · 层 C 详设：机会发现

## 5.1 接缝分类学（对 spec 的静态查询）

| # | 接缝类型 | 查询 | 已验证实例 | 强制零假设 |
|---|---|---|---|---|
| 1 | Clamp / floor / cap | 找 clamp 算子，解饱和域 | funding 死区 −4bp~+6bp，46–73% 小时数落入 | 死区内本来就没人交易 |
| 2 | 控制量／计价量失配 | 找「A 决定、按 B 计价」且 B/A 大 | impact notional $6k 决定按 $79M OI 收的 funding → AAVE 34,830× | 维持压制的对抗成本 > 收益 |
| 3 | 冻结／陈旧状态 | 找 `frozen_when` / `heartbeat` / `deviation_threshold` | HIP-3 休市冻结 external；跨链 feed 差 1–2 数量级 | **价差只是在给期货曲线／持有成本定价** |
| 4 | 强制流 | 找 `on: cond → forced_action` | 清算 20%/30s、ADL、重开强制结算 | 强制流不经过你能触及的场所（10/10 有 62.6% 走 backstop） |
| 5 | 阈值离散跳变 | 找分段函数断点 | >$100k 整仓→20%；margin tier 边界；重锚定用尽 | 跳变点已有人守 |
| 6 | 更新频率失配 | 对比各状态 `freq` | oracle 3s vs CEX 连续；Optimism 领先 Arbitrum 19.4s | 延迟窗口 < 你的执行延迟 |

## 5.2 候选登记簿（`registry`）

**数据模型**：

```
Candidate {
  id                  : uuid
  spec_ref            : "hyperliquid.perp.funding.clamp"   # 必填，指向 spec 字段
  seam_type           : 1..6                                # 必填
  null_hypothesis     : text                                # 必填
  falsify_script      : path                                # 必填，可运行
  threshold_hash      : sha256                              # 必填，看数据前锁定
  state               : 候选 | 证伪中 | 已否决 | 已确认 | 已上线 | 已退役
  evidence            : [run_id...]
  proposer            : agent_id | human
  created_at, updated_at
}
```

**入库校验（程序强制，非约定）**：五项必填缺一拒收。`threshold_hash` 必须在 `falsify_script` 首次运行**之前**提交，运行时校验哈希一致——**这是防 p-hacking 的机制化手段。**

**状态机**：
```
候选 ──► 证伪中 ──┬──► 已否决（零假设未被证伪）
                  └──► 已确认 ──► （走 gauntlet）──► 已上线 ──► 已退役
```
`已上线` 的候选被场所监控持续盯；对应 spec 字段漂移 → 自动降级回 `证伪中`。

## 5.3 证伪流水线

**排序键**：`priority = 1 / (证伪所需时间 × 证伪所需新基建)`
**按证伪成本排序，不按预期收益排序**——吞吐量来自快速淘汰，不是来自押中。

**首批必须跑的**：石油永续 funding（CL −24.97%/年、Brent −16.54%）对 WTI/Brent 期货曲线 roll yield 的归因回归。零假设「只是在给 backwardation 定价」——**目前未被证伪**。两种结论都算达成，因为都推进了知识。

# 第六部分 · 层 D 详设：建模

## 6.1 D1 · 泄漏探针与天花板度量（`diagnostics`）

**优先级最高之一，成本几天，能否定大片下游工作。全程并行，不等任何依赖。**

| 诊断 | 方法 | 判读 |
|---|---|---|
| **泄漏探针** | 把 forward return 直接当特征喂进管道 | 学不会 → **管道故障**，停止一切新算法工作（FinRL #1248 就是这个结果） |
| **信息天花板** | `RMSE(I) = σ·e^{−I}`，互信息估上界 | 与现有模型差距小 → 换模型是浪费，去换信息集 |
| **样本充分性** | `T_crit = C_z⁻¹σ²logP / B²` | R²=2–3% 时 P=12,000 需约 31 年；P=15 也要约 9 年 |

**两者进 CI，任何管道改动后自动跑。**

**背景警示**：Qlib 有两个已记录的污染源——`NORM` 在 train/test 切分**前**执行导致泄漏（维护者只加文档未改默认，而这是 Alpha158 默认路径）；仅改 test 段结束日期，同股同日预测分数差 0.8445。**既有因子结论可能双向污染。**

## 6.2 D2 · m 通道特征层（`features-m`）

**这是 CEX 上拿不到的输入，也是 CTA 在本平台可以严格更强的原因。**

| 特征族 | 内容 | 来源 |
|---|---|---|
| 清算图 | 按 (market, price_bucket) 的强平量分布、距当前价的分位 | A2 全局状态 |
| 机制状态 | `premium`、`impact_bid/ask`、距 clamp 边界的余量、funding 累积 | A1 + B1 |
| 会话状态 | 距重开时长、discovery bounds 剩余空间、重锚定计数、external 冻结价与 oracle 的差 | B1（HIP-3） |
| 跨场所 basis | HL vs 币安 vs HIP-3 vs 标的现货 | A1 + 外部行情 |
| 强制流历史 | 清算/ADL 事件流、backstop 占比 | A2 |

**硬要求：每个特征有 point-in-time 保证**——回测取到的值 = 当时可得的值，有测试证明。这是唯一能防住这一层引入前视偏差的手段。

## 6.3 D3 · price 模块（`price`）

**契约**：
```
predict(context, horizon) -> Distribution over p_{t+h}
```

**必须是分布，不是点估计**——MPC 需要分位数设风险约束；点估计会让你在尾部裸奔。

**两种 price**：
- `p̂` 外生价格在未来 h 的分布 → MPC 的不确定性输入
- `v̂` 标的公允价（尤其**无市可参考时**，如 HIP-3 休市期间）→ 基差归因、mark 合理性

**独立记账（硬要求）**：预测器指标（PIT / CRPS / 条件 IC / 按 horizon 分层）与策略指标**分离存储**。必须随时能回答：「这次变好，是预测变好了还是规划变好了？」

# 第七部分 · 层 E 详设：策略与仿真

## 7.1 三档保真度

| 档 | 是什么 | 基于 | 给你什么 | 已知缺陷 |
|---|---|---|---|---|
| **T1 重放** | 真实簿 + 真实 funding + 真实清算规则，**对手冻结** | Nautilus backtest | 机械层的精确性 | 对手不对你反应 |
| **T2 反应** | 同一起点，注入**校准过的**响应 agent | T1 + agent 层 | 反身性溢价 Δ(T1,T2)，按下单规模分层 | 校准不过则结果不可用 |
| **T3 影子** | 实时 listen-only，不提交订单 | Nautilus sandbox | **真实世界机械层地面真值，不需资金** | 无成交反馈 |

**T2 的校准目标必须链上可观测**（例：历史上一个 X bp 的簿价偏移，平均在多少秒内被套利者收敛）。校准不通过 → T2 结果**不得用于决策**。

## 7.2 策略骨架

```
policy = f_θ(structural_skeleton, state)
```

- **骨架是解析解**（Almgren-Chriss、Avellaneda-Stoikov、会话收敛的规则式解），不是随机初始化的网络
- **RL / 优化只调少量参数**（风险厌恶、偏斜、执行比例、报价深度）
- **最坏退化回骨架**，不是退化到发散的网络

**证据**：Wang/Gao/Li（*Finance and Stochastics* 2026）用 AC 闭式解参数化 → 参数极少 → 有线性收敛证明 → 同时打败 plug-in 经典控制与深度 model-free SAC；Alpha-AS（PLOS ONE 2022）RL 只调 AS 的风险厌恶与偏斜；Hendricks & Wilcox RL 只调执行比例 → IS 改善 4.8–10.3%。
**反面**：Spooner（AAMAS 2018）full-state 自由出价 agent 在 10/10 只股票上为负且训练发散。

**MPC 实测锚点**：Bayforest + Bertsekas（arXiv:2603.28898）——求解器 **Clarabel**，**约 1 ms/决策**，动作空间 **d=11**；相对 spread-crossing 基准降低 40–50% schedule shortfall。

**求解器选型**：先用 `qpsolvers` 在真实问题维度跑基准；热路径在 Rust 且含方差/锥约束 → Clarabel；纯 QP 且参数逐 tick 微变 → OSQP（warm start + codegen）；含离散决策 → HiGHS。

## 7.3 基线是一等公民

**每个 spec 配一个自适应基线**，且基线参数**经优化并留有优化记录**（防稻草人）。

**依据**：Solovyev(2019) 的唯一严格对比中，自适应 Almgren-Chriss **打败了每一个 RL 配置**；Gašperov 综述里 22 篇 RL 做市论文 **22/22 全报正面结果，只有 18% 用了 AS/GLFT 基线**。

**基线弱 = 你测的是「自适应打败非自适应」，跟 RL 无关。**

## 7.4 CTA 通路

**支持，且可以严格更强**：CTA 是 `m` 很薄的特例，但它**可以吃到 D2 的 m 特征**（清算图、机制状态、跨场所 basis）——这是 CEX 上的 CTA 拿不到的输入。

**但不开后门**：CTA 走**同一条 gauntlet**，照样过 D1 泄漏探针与天花板度量。平台支持它，不等于它成立——**CTA 的 edge 仍在 `p` 上，而 `p` 有信息天花板。**

## 7.5 八关 gauntlet

| 关 | 检查 | 不过意味着 |
|---|---|---|
| **G0** | spec 重放一致性（三方对账） | 先修 spec |
| **G1** | 泄漏探针 | 管道坏了，停止新算法工作 |
| **G2** | 信息天花板 | 别换模型，换信息集 |
| **G3** | 自适应基线有正期望且实现公平 | 后续任何「优势」无意义 |
| **G4** | 跨 ≥10 随机种子的分布 | 差距被方差淹没 → 记为负面结果 |
| **G5** ★ | **证伪审计**：零可预测性合成数据上，**整条流水线**收益 95% CI 覆盖 0 | 工作流有泄漏，前面全部作废 |
| **G6** | T2 校准通过 + Δ(T1,T2) 已量化 | T2 结果不可用于决策 |
| **G7** | T3 影子 ≥4 周含**至少一次高波动事件** | 状态重建有系统性错误 |
| **G8** | 小额真钱，偏差可归因 | 停 |

**「快」来自不用每次重新设计验证，不是来自跳过验证。**

**实验矩阵**：所有结果按 `策略 × 保真度档 × 种子 × spec 版本` 四维存储，可按任一维切片。

# 第八部分 · 层 F 详设：执行、风控、运维

## 8.1 执行（`execution`）

- 订单生命周期与状态机 → **用 Nautilus 的**，不自造
- 执行对账 → **用 Nautilus 的 execution reconciliation**
- 必测路径：拒单、超时、部分成交、reduce-only、post-only 被拒、bounds 内外
- sandbox 模式下 **100% 订单可对账**

## 8.2 风控（`risk`）

**事前限额检查（每笔单，从 spec 直接算）**：

| 检查 | 来源 |
|---|---|
| 订单名义额 ≤ `max_market_order_ntl` | spec constraints |
| 距 `liq_price` 余量 ≥ 阈值 | spec liquidation |
| discovery bounds 剩余空间 ≥ 阈值 | spec（HIP-3） |
| 单市场敞口 / 总敞口 ≤ 限额 | 风控配置 |
| 重锚定计数未耗尽 | spec（HIP-3） |

**kill switch 三级**：降规模 → 只减仓 → 全平。触发条件写在 spec 里（如 bounds 重锚定次数耗尽、funding 触及 4%/h 上限、对账 CI 变红）。**三级均需演练通过。**

## 8.3 私钥与权限

- **签名服务独立进程**。策略进程**不持有私钥**，只能提交经限额校验的意图。
- **有测试证明策略进程无法取得私钥。**
- 权限最小化；每个环境（sandbox/live）独立密钥。

## 8.4 偏差归因

**实盘 vs 影子的每一笔偏差，必须能归因到具体的 spec 字段。** 归因不了的偏差 = spec 缺陷 → 回 G0。

**这是 F4 放量的唯一依据**：连续 N 日无不可归因偏差才放量，规则**由代码强制**，不是人工纪律。

## 8.5 运维（`ops`）

- 节点追块延迟告警
- 行情缺口告警（缺口率超阈值）
- 对账 CI 红灯 → 自动降级到只减仓
- **任一事故可由事件流完整重放**（事件溯源，Nautilus 已提供）
- **高波动降级路径演练**：限速劣化、节点落后、行情缺口三种场景各演练一次

**⚠️ 必须记住**：所有速率、深度、还原率的实测都在清淡日做的。**10/10 那种事件中 API 限速、节点追块能力都可能显著劣化——而那正是最需要它工作的时刻。** T3 影子必须跨越至少一次高波动事件才算通过。

# 第九部分 · 层 G 详设：Agent 编排

## 9.1 唯一组织规则

> **Agent 产出 = 提议。每条提议落到一个预注册的、机器可判定的验收上。Agent 不是任何验收的裁判。**

**依据**：模型、worker、检索内容、工具输出**不能创造或扩大权限**；**不得在缺少环境证据时报告成功**。

**本项目的特殊条件**：存在**真值预言机（链上状态）**，agent 产出可被机械判真假。这是 agent 层在此安全的根本原因，也是它在多数交易系统里不安全的原因。

## 9.2 六个岗位

| Agent | 形状 | 产出 | 预注册验收 | 权限 |
|---|---|---|---|---|
| **spec 起草员** | native tool loop | 会计核心代码草稿 | **三方对账通过** | 写分支，不能合并 |
| **漂移分诊员** | 事件触发 workflow | 定位漂移字段 + 补丁 | 补丁重跑对账通过 | 写分支，不能合并 |
| **接缝提议员** | 单次调用／有界循环 | 候选（5 项必填） | **schema 校验**，缺项拒收 | 写登记簿 `候选` 态 |
| **证伪执行员** | coded workflow，agent 只在两端 | 跑测试、写结论 | 阈值哈希在运行前锁定 | 只读 + 写结论 |
| **场所监控员** | 定时 | 文档/公告/链上参数变更提示 | 只提示，转分诊员 | 只读 |
| **实验归因员** | 单次调用 | 解释 gauntlet 矩阵变化 | **纯咨询，永不成为闸门** | 只读 |

## 9.3 硬禁止

Agent 不得：进入下单决策路径｜评判策略是否有效｜选择或修改阈值｜绕过 conformance 改 spec｜接触私钥或资金路径｜以「另一个模型认可了」作为通过依据｜直接写主分支。

## 9.4 信任边界

**场所文档、治理论坛、changelog 是外部不可信内容。** 它们可以促成 spec 变更提议，**不能授权变更**。唯一授权者是对账通过。

**安全推论**：若有人能影响监控 agent 读到的内容，理论上可尝试注入错误的 spec 变更——**但错的 spec 过不了链上真值对账。预言机本身就是防线。**

## 9.5 失败与恢复

- Agent 失败（超时、工具错误、拒绝）→ **typed 状态，不是静默成功**
- 提议被拒 → 保留提议与拒因，可人工接手；**不清空无关能力**
- 预算耗尽 → typed pause，保留已完成工作
